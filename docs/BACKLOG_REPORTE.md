## Reporté par l'exécution de la nuit (ajouté au fil de l'eau)

| Quoi | Pourquoi |
|---|---|
| La suite sous un rôle **sans** BYPASSRLS | L'application ne pose pas le locataire par transaction (`set_config('otto.tenant_id', …, true)` dans chaque requête) : sous un rôle non-bypass, chaque lecture rend zéro ligne et `seedBase()` est refusé dès `tenant` (éprouvé par la revue hostile sur PGlite avec 0033). Le rôle de CI a donc BYPASSRLS, comme la production. C'est le chantier R9 sous un autre nom — il se fait le jour, pas la nuit. Le bloc d'assertions du build le DIT au lieu d'afficher « RLS forcée ». |
| Le secret `OTTO_CI_DATABASE_URL` | Ne peut être posé que par le fondateur (GitHub → Settings → Secrets). Le travail `rôle de production` reste rouge tant qu'il manque, et le dit. |
| Index unique sur `entity(tenant_id, forme normalisée du nom)` et contrainte d'exclusion sur les exercices d'une entité | Le doublon et le chevauchement sont refusés par le service ; deux créations simultanées sur le pooler passent toutes les deux. Poser l'index exige de vérifier d'abord qu'aucune base existante ne le viole — le jour, pas la nuit. |
| Les tables de libellés `Record<string, string>` à clés-codes, hors de vue du détecteur de langue | `{ reviewer: 'réviseur' }` ne porte aucun des six noms de propriété que la règle lit. Les six tables du dépôt sont nommées dans `src/lib/langue.ts` ; la seule affichée (`NOM_VISA`) est passée en clés. La règle qui les lirait toutes doit avoir son cas connu mauvais avant d'exister. |
| Le lien « Dossier N-1 » de l'en-tête sans vérification de l'appartenance du lecteur | Il peut mener à un refus `requireMember` — un refus nommé, pas une fuite. Le masquer ou l'annoncer demande un choix d'écran. |
| Les sections d'un dossier dont la vue d'ensemble n'a jamais été ouverte | Elles naissent à l'ouverture de la vue d'ensemble (`assurerSections`) ; le tableau de bord les lit sans les créer, et le dit sur l'écran. Les créer à la création du dossier est une décision de modèle, pas de nuit. |
| L'ancienneté des notes en jours OUVRÉS | Le tableau de bord compte en jours calendaires et le dit ; les jours ouvrés (calendrier du cabinet, jours fériés par pays) sont l'affaire de la file de revue (1.4). |
| Fixtures de FAUX POSITIF par famille d'obstacle, et fichiers d'or (sélections par graine, seuils, totaux, familles par dossier, routes, clés par locale, politiques RLS, grants) | Chacun est un instrument, et un instrument s'éprouve d'abord contre un cas connu mauvais (règle 17) ; la nuit a construit le registre et son épreuve, pas ces huit fichiers. Les familles sans test sont écrites « aucune preuve » dans GUARDS.md. |
| L'inventaire des applications informatiques (système source de l'IPE) | Texte libre cette nuit ; un référentiel d'applications par cabinet est un objet de modèle, pas de nuit. |
| La balance auxiliaire comme `import_file` | Elle est une PIÈCE (`aux_balance_file` → evidence) ; un rapport IPE la désigne par `evidence_id`. Le critère « importer la balance âgée puis remplir le bloc IPE » se joue sur le grand livre importé. |
| Le format de date du panneau IPE (AAAA-MM-JJ) | Hérité de 0031 ; le reste du produit saisit jj/mm/aaaa. À aligner en une fois, avec le peuplement et le parcours qui le lisent. |
| L'erreur d'hydratation React #418, intermittente | Vue deux fois sur cinq parcours de nuit, sur deux écrans différents (écarts, papier), jamais au même endroit ; le harnais la compte en échec, à raison. Aucune hypothèse n'a été prouvée (le rail ne lit pas localStorage au rendu initial — vérifié) ; l'ADR-094 post-scriptum l'avait attribuée à l'attente après action serveur. À instrumenter en développement (build non minifié) avant de conclure. |
| Trente et une tables à `engagement_id` sans garde de verrou (liste figée dans gardes.test.ts) | 0003 n'en posait que sur dix-neuf tables ; chaque migration depuis en a créé d'autres. Les garder toutes à l'aveugle a fait échouer la CLÔTURE du parcours (le journal et l'archive s'écrivent après le scellé). Le tri — lesquelles sont de la documentation à sceller, lesquelles s'écrivent après — se fait de jour, table par table ; d'ici là toute table NOUVELLE doit être gardée ou inscrite avec sa raison. |
| `exception_quantified_needs_disposition`, retirée en 0037 | Inerte depuis 0009 (CHECK à NULL satisfait), puis recouverte par la résolution probante même réécrite : aucune attaque ne l'atteint seule. L'invariant vit dans G-05. Si un jour une résolution sans disposition devait être permise pour un écart NON chiffré, la contrainte reviendrait — avec son épreuve. |
